# Панель управления «Раскадровки» — дизайн

Дата: 2026-09-09. Основа: разбор функционала и четыре вопроса с ответами «A» (сессия
2026-09-08), макет `panel/mockup.html` (тег `v2-panel-direction-11`), контракты
`docs/superpowers/specs/2026-09-07-raskadrovka-design.md`.

## 1. Цель и рамки

Локальное веб-приложение, из которого книга проходит весь путь до иллюстраций без терминала:
загрузить файл, настроить разбор, отобрать героев и сцены, собрать библию и листы, написать
карточки, сгенерировать кадры, принять их и опубликовать галерею. Отдельная область — стили.

Первая версия — **вертикальный срез**: одна книга через все этапы, каждый экран минимальный,
всё на настоящих данных Red Rising, которые уже лежат в репозитории. Что отложено — в §11.

Панель ничего не хранит у себя. Состояние — файлы репозитория по действующим контрактам;
панель их читает, пишет и запускает те же скрипты, что и человек в терминале. Любой шаг можно
сделать руками, и панель это увидит.

## 2. Принятые решения

| вопрос                                                                   | решение                                                                                  |
|--------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| Кто исполняет шаги с суждением (библия, аудит, карточки, стиль из книги) | Панель сама вызывает агента, без диалога                                                 |
| Кто отбирает героев и сцены                                              | Человек на гейте; без отметок «дальше» не работает                                       |
| Какой агент                                                              | Codex CLI — тот же, что рисует; скиллы читает из `.claude/skills/` по указанию в задании |
| Объём первой версии                                                      | Вертикальный срез                                                                        |

Допущения, принятые без возражений: сервер на стандартной библиотеке Python 3.10 в `panel/`,
одна HTML-страница без сборки; задания живут в процессе сервера, очередь и логи — в
игнорируемом `cache/`; git руками (панель показывает статус); статические `index.html` и
`styles/index.html` остаются публичной витриной, панель их пересобирает.

## 3. Архитектура

```text
panel/
  server.py        ThreadingHTTPServer: GET /api/* — JSON из файлов, POST/PUT /api/* — действия,
                   GET /file/<путь> — картинки и тексты из разрешённых папок, GET / — страница.
                   Здесь же обработчики заданий: они связывают scripts/ и агента с очередью
  jobs.py          очередь: один рабочий поток, задания по одному, запись в cache/panel/jobs/
  agent.py         Codex: сборка инструкции из шаблона, запуск, проверка результата, повтор
  validators.py    контрактные проверки записей библии и карточек — общие для агента и редактора
  settings.py      значения по умолчанию и чтение cache/panel/settings.json
  tasks/
    bible-entry.md шаблон задания «запись героя в библию с аудитом»
    scene-card.md  шаблон задания «карточка сцены»
  index.html       одна страница, экраны переключаются на месте, опрос /api/jobs раз в 2 с
  mockup.html      визуальный контракт (не исполняется)
scripts/
  generate_sheet.py   лист персонажа через Codex — из scratchpad, с CLI
  generate_scene.py   кадр сцены через Codex — из scratchpad, с CLI
```

Сервер импортирует `scripts/` как библиотеку: `ingest_book.ingest()`, `index_book`,
`build_prompt.build()`, `register_result.register()`, `check_rights.check_all()`,
`build_gallery.main()`, `build_styles_page.main()`. Codex — только подпроцессом.

Один рабочий поток нарочно: Codex один, кадры идут по одному, очередь читаема. Быстрые
детерминированные шаги (разбор, индекс, сборка промпта, регистрация) тоже идут через очередь,
чтобы порядок был один и лог общий.

Загрузка книги — multipart, разбирается стандартным `email.parser.BytesParser`; файл ложится в
`books/<slug>/source/`. Раздача `/file/` — только из `output/`, `styles/refs/`,
`compositions/refs/`, `books/*/characters/`, `books/*/*/input/`, `books/*/*/prompt/`, с
проверкой, что путь после `resolve()` лежит внутри корня.

## 4. Задания и очередь

Задание — JSON в `cache/panel/jobs/<id>.json`:

```json
{"id": "20260909-1041-07-sheet-ugly_dan", "kind": "sheet", "args": {"slug": "…", "key": "ugly_dan"},
 "status": "running", "created": "…", "started": "…", "finished": null,
 "attempts": 1, "error": null, "log": "cache/panel/jobs/<id>.log"}
```

Статусы: `queued`, `running`, `done`, `failed`, `interrupted`, `cancelled`. При старте сервера
задания в `running` помечаются `interrupted`, а стоявшие в `queued` возвращаются в очередь:
перезапуск панели — дело обычное и не должен тихо терять работу. Повторный запуск любого вида
пропускает уже существующие результаты — так уже работает раннер сцен.

Задание, у которого вид и аргументы совпадают с уже открытым, в очередь не берётся: ответ
409 с номером того задания. Шаг с суждением идёт минутами, и второй запуск того же — не
удвоенная скорость, а два Codex на одном файле.

Снятие задания на ходу гасит и повтор: убитый процесс со стороны раннера неотличим от
неудачной попытки, и без явного признака «снято» вторая попытка началась бы сама.

Виды заданий первой версии:

| kind          | что делает                                              | чем                                                |
|---------------|---------------------------------------------------------|----------------------------------------------------|
| `ingest`      | файл → `book.json`, `cache/<slug>/paragraphs.jsonl`     | `ingest_book`                                      |
| `index`       | индекс лиц, мест, кандидатов; параметры и диапазон глав | `index_book`                                       |
| `bible-entry` | запись героя с локаторами и аудитом                     | Codex по `tasks/bible-entry.md`                    |
| `sheet`       | лист персонажа                                          | `generate_sheet` (Codex)                           |
| `scene-card`  | карточка сцены партии                                   | Codex по `tasks/scene-card.md`                     |
| `prompt`      | промпт сцены в `prompt/`                                | `build_prompt`                                     |
| `scene`       | кадр сцены                                              | `generate_scene` (Codex)                           |
| `register`    | записи манифеста по плану, регистрация, права, галерея   | `register_result`, `check_rights`, `build_gallery` |
| `styles-page` | пересборка `styles/index.html`                          | `build_styles_page`                                |

`POST /api/jobs/<id>/cancel`: из `queued` — в `cancelled`; из `running` — убить подпроцесс, в
`cancelled`; файл-результат, если успел появиться, остаётся.

## 5. Раннер агента

Одно задание с суждением — одна сущность: один герой, одна сцена. Проверка и повтор точечные.

**Инструкция** собирается из `panel/tasks/<kind>.md` подстановкой полей. Обязательные части:
какой скилл прочесть и следовать ему (`.claude/skills/raskadrovka-characters/SKILL.md` или
`raskadrovka-book`); книга и сущность; где читать текст (`python3 scripts/show_paragraphs.py`,
абзацы из индекса); куда и по какому контракту писать; что не трогать; не коммитить.
Шаблоны коммитятся — они часть провенанса библии и карточек.

**Запуск:** `codex exec -s workspace-write --skip-git-repo-check -C <корень> --ephemeral
"<инструкция>"` с закрытым stdin, таймаут из настроек (по умолчанию 20 минут), лог в файл задания.
Сама командная строка берётся из настроек (`codex_cmd`, §6) списком аргументов, инструкция
подставляется на место `{prompt}`; в коде лежит только значение по умолчанию. Иначе тест не
может подсунуть поддельный `codex`, а человек — сменить профиль или модель, не правя панель.

**Проверка результата** (`validators.py`), после каждой попытки:

- ожидаемый файл существует и разбирается как JSON;
- проходит контрактные проверки своего вида (§6);
- в дереве изменились только ожидаемые пути. Дерево во время работы почти всегда грязное,
  поэтому сравниваются **два снимка** `git status --porcelain` — снятый прямо перед запуском
  Codex и снятый после: провал даёт разница множеств, а не сам факт правок. Ожидаемые пути:
  `bible-entry` — `books/<slug>/bible.json`; `scene-card` — `<партия>/scenes/<NN>-*.json`;
  `scene` — кадр в `output/` и `<партия>/metadata/plan.json`, куда задание пишет `card_sha256`.
  Посторонние изменения — провал с перечнем, панель их не откатывает.

Провал → одна повторная попытка, в инструкцию дописываются претензии валидатора дословно.
Второй провал → задание `failed` с отчётом; сущность правится руками в редакторе панели.

**Заготовки для агента**, чтобы он не выбирал имена сам: у карточки панель задаёт порядковый
номер `NN`, агент выбирает только слаг; валидатор ищет файл по префиксу `scenes/NN-`.

## 6. Данные и контракты

Действующие контракты не ломаются. Расширения:

**`bible.json`, герой** — поле `audit`: десять атрибутов с баллом `0 | 0.5 | 1`, ключи
`age, build, face, eyes, hair, skin, clothing, gear, marks, bearing`; `understanding` равен их
сумме. Проверка: ключи ровно эти, значения из множества, сумма сходится.

**У претензии валидатора два уровня.** `error` — запись противоречит себе или книге: локатор
указывает не на ту главу, балл не сходится с клетками, английское поле написано кириллицей.
`missing` — поля контракта в записи ещё нет; чаще всего оттого, что запись писали до того,
как поле появилось: разбивка `audit` — ровно такой случай, все восемь записей Red Rising
старше её. Красным горит только `error`; иначе «не доделано» и «сломано» неразличимы, экран
краснеет целиком и перестаёт что-либо сообщать. Уровень по умолчанию — `error`, исключение
называется явно: забытая обёртка должна делать претензию строже, а не безобиднее.

**`<партия>/metadata/plan.json`** — что задумано до появления кадров:

```json
{"short": "proba", "style": "tush-i-plashki",
 "scenes": [{"order": 1, "chapter": 2, "paragraphs": [57, 58], "id": null, "card_sha256": null,
             "style": null, "style_refs": ["ref-01", "ref-03"], "composition": "01-dvoe-litsom"}]}
```

`id` заполняется, когда агент написал карточку; `card_sha256` — хеш карточки в момент
генерации кадра, его пишет задание `scene`; `style` у сцены — только для партии-пробы, где
каждая сцена идёт своим направлением, иначе `null` и берётся общий.

`short` — короткое имя партии в имени файла кадра
(`output/<книга>--<short>--<направление>--<карточка>.png`). Отдельное поле, а не имя папки:
папка называется `01-proba-stiley`, а в именах кадров стоит `proba`, и вывести одно из другого
нельзя. Панель предлагает `short` при создании партии и проверяет, что он не занят.

**Кто заводит запись в манифесте.** `register_result.register()` умеет только обновлять уже
существующие записи `scenes`: он читает у записи `card`, `style`, `style_refs`, `composition`,
`prompt`, `output` — то есть замысел, которого сам не знает. Поэтому задание `register` перед
вызовом `register()` **досевает** манифест: для каждой сцены плана, у которой есть карточка и
кадр, но нет записи, оно создаёт запись из плана и карточки —

| поле                                 | откуда                                                       |
|--------------------------------------|--------------------------------------------------------------|
| `id`                                 | `<направление>--<имя карточки без расширения>`               |
| `title`, `caption`, `order`          | карточка (`title` + ` — <направление>`, если стиль у сцены свой) |
| `style`                              | сцена плана, иначе общий `style` плана                        |
| `style_refs`, `composition`          | план сцены                                                    |
| `card`, `prompt`                     | `scenes/<файл>.json`, `prompt/<id>.txt`                       |
| `output`                             | `../../../output/<книга>--<short>--<id>.png`                  |

Существующие записи не переписываются: хеши, входы и снимки `input/` остаются делом
`register()`. Так замысел заводит панель, а факт по-прежнему пишет один скрипт.

**Листы: принятие без нового поля в библии.** Задание `sheet` из панели пишет лист и промпт в
`cache/panel/<slug>/sheets/<key>.png|.txt`, а не в `characters/`. «Принять» переносит файл в
`books/<slug>/characters/<key>.png` и записывает в библию `sheet`, `sheet_sha256`,
`sheet_prompt` — ровно как сегодня делает человек. Эти три поля ведёт панель, а не агент:
задание `bible-entry` переписывает запись целиком и роняет их, поэтому обработчик запоминает
их до запуска и возвращает после — судить агенту, вести учёт панели. «Отклонить» переносит файл в
`refs-local/sheets-rejected/<key>-<дата>.png`. «Перегенерировать» при принятом листе сначала
переносит прежний в `refs-local/sheets-rejected/` и снимает поля из библии. Так в библии по
определению лежат только принятые листы, и признак «принят» — наличие `sheet` с совпадающим
хешем. `generate_sheet.py` из терминала пишет сразу в `characters/`: человек, запустивший его
сам, и есть приёмка.

**`<партия>/metadata/review.json`** — вердикты, коммитятся:

```json
{"03-ugly-dan-kidaet-kamen": {"verdict": "accepted", "reason": "", "at": "2026-09-09T10:41:07"}}
```

`verdict`: `accepted`, `regenerate`, `rejected`. Регистрация доступна, когда у каждой сцены
плана вердикт `accepted`.

**Карточка сцены** — проверки валидатора (те же, что покажет редактор):

- отрывок — целые абзацы: каждый абзац находится по `paragraph_sha256`, абзацы подряд, одна глава;
- локатор вычисляется из отрывка, а не берётся из файла: панель перезаписывает `locator`;
- для `protected`: ≤ 2 абзацев, ≤ 1500 знаков, сумма по книге ≤ 3 %;
- `invariants` — ключи библии, у каждого есть принятый лист;
- `composition` — `null` или id шаблона из `compositions/templates/`;
- `details` непустой; цветовые эпитеты в `details`/`setting`/`mood` — предупреждение, не провал
  (словарь: названия цветов и «-цветный», «свечение» с цветом);
- `frame.characters[].ref` ⊆ `invariants`.

**Локальное, не в git** — `cache/panel/<slug>/panel.json`:

```json
{"toc_confirmed": true,
 "heroes": {"Darrow": {"key": "darrow", "in_bible": true, "needs_sheet": true}},
 "places": ["Lykos"],
 "scenes": [{"chapter": 2, "paragraphs": [57, 58], "note": "Урод Дэн кидает камень"}],
 "index_params": {"per_chapter": 3, "window": 2, "total": null, "min_mentions": 4, "chapters": [1, 3]}}
```

Ключ героя (`key`) — транслитерация имени из индекса, редактируется человеком до сборки библии.

**Настройки** — `cache/panel/settings.json`, при отсутствии — значения по умолчанию из кода:

```json
{"codex_cmd": ["codex", "exec", "-s", "workspace-write", "--skip-git-repo-check",
               "-C", "{root}", "--ephemeral", "{prompt}"],
 "timeout": 1200, "attempts": 2, "max_style_refs": 3}
```

`{root}` и `{prompt}` подставляются панелью; остальные аргументы идут как есть.

## 7. API

Все ответы — JSON; ошибки — `{"error": "…"}` с кодом 400/404/409. Действия, которые долго
идут, возвращают `{"job": "<id>"}`.

| метод и путь                                                          | что                                                                                                       |
|-----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| `GET /api/books`                                                      | книги с прогрессом по этапам                                                                              |
| `POST /api/books`                                                     | multipart: файл + метаданные + права + параметры разбора → job `ingest`                                   |
| `GET /api/books/<slug>`                                               | `book.json`, оглавление, `panel.json`, состояние гейтов                                                   |
| `PUT /api/books/<slug>/panel`                                         | отметки: оглавление подтверждено, герои, места, сцены, параметры индекса                                  |
| `POST /api/books/<slug>/index`                                        | job `index` с параметрами из `panel.json`                                                                 |
| `GET /api/books/<slug>/index`                                         | `cache/<slug>/index.json`                                                                                 |
| `GET /api/books/<slug>/paragraphs?chapter=&from=&to=&grep=`           | абзацы из кеша — читалка                                                                                  |
| `GET /api/books/<slug>/bible`                                         | `bible.json`                                                                                              |
| `PUT /api/books/<slug>/bible/<key>`                                   | правка записи руками; валидатор                                                                           |
| `POST /api/books/<slug>/bible/<key>`                                  | job `bible-entry`                                                                                         |
| `PUT /api/books/<slug>/bible/<key>/audit`                             | правка клеток аудита                                                                                      |
| `POST /api/books/<slug>/sheets/<key>`                                 | job `sheet`; `{"regenerate": true}` убирает прежний лист в `refs-local/sheets-rejected/`                  |
| `PUT /api/books/<slug>/sheets/<key>`                                  | `{"accepted": true}` или `{"rejected": true}`                                                             |
| `GET /api/books/<slug>/batches`                                       | партии с состоянием                                                                                       |
| `POST /api/books/<slug>/batches`                                      | создать партию: имя, текст запроса, направление, сцены из отбора → папка, `plan.json`, README с маркерами |
| `GET /api/books/<slug>/batches/<b>`                                   | план, карточки с результатами валидатора, промпты, кадры, вердикты                                        |
| `PUT /api/books/<slug>/batches/<b>/plan`                              | эталоны и шаблон на сцену                                                                                 |
| `POST /api/books/<slug>/batches/<b>/cards/<NN>`                       | job `scene-card`                                                                                          |

| `POST /api/books/<slug>/batches/<b>/generate`                         | jobs `prompt` + `scene` на сцены без кадра; `{"scenes": [...]}` — на выбранные                            |
| `PUT /api/books/<slug>/batches/<b>/review/<id>`                       | вердикт; `regenerate` удаляет кадр и ставит job                                                           |
| `POST /api/books/<slug>/batches/<b>/register`                         | job `register`                                                                                            |
| `GET /api/styles`                                                     | направления с эталонами                                                                                   |
| `POST /api/styles/page`                                               | job `styles-page`                                                                                         |
| `GET /api/jobs`, `GET /api/jobs/<id>`, `GET /api/jobs/<id>/log?tail=` | очередь и логи                                                                                            |
| `POST /api/jobs/<id>/cancel`                                          | снять или прервать                                                                                        |
| `GET /api/git`                                                        | `git status --porcelain`                                                                                  |
| `GET /file/<путь>`                                                    | файл из разрешённых папок                                                                                 |

## 8. Экраны первой версии

Слева навигация: **Книги · Стили · Задания**. Внутри книги этапы по порядку, у каждого виден
гейт. Экран этапа — пронумерованные шаги, у каждого состояние и своя кнопка; внизу гейт с
«Назад» и «Дальше»; сверху «Шаг N из 4» с теми же переходами.

1. **Книги.** Список с прогрессом. Форма приёма: файл, slug, метаданные, права с обоснованием,
   параметры разбора. После разбора — оглавление с предупреждениями (глава короче 300 знаков,
   глава больше 25 % книги), «переразобрать». Гейт: «оглавление верное».
2. **Лица и сцены.** Параметры индекса и диапазон глав. Таблицы: лица (упоминания, вид, главы,
   первый абзац, абзацев с внешностью; отметки «в библию», «нужен лист»; правка ключа),
   места, кандидаты (балл, превью, «окрестности» открывают читалку ±3 абзаца, «взять»).
   Сцена вручную: глава и диапазон. Гейт: есть хотя бы один герой с отметкой «нужен лист» и
   одна сцена.
3. **Персонажи.** Шаг 1 — библия и аудит: вкладки героев, полоса из десяти клеток, считка
   «из книги» и «в промпт», кнопки «Собрать запись», «Править описание», «Добрать из книги»
   (открывает читалку с grep-пресетами внешности). Шаг 2 — листы: карточки с принятием,
   перегенерацией, отклонением; «Сгенерировать листы» ставит задания на героев с аудитом ≥ 8
   без принятого листа. Шаг 3 — в библии без листа, тумблер «нужен лист». Гейт: у всех с
   отметкой лист принят.
4. **Партии.** Список; создание. Внутри партии вкладки:
   - **Карточки** — план сцен, «Написать карточку» на сцену и «Написать все», редактор полей
     `frame` с живыми проверками §6, предпросмотр промпта. Гейт: все карточки зелёные.
   - **Генерация** — эталоны и шаблон на сцену, «Сгенерировать», прогресс по сценам, попытки,
     хвост лога, «Остановить». Гейт: у всех сцен есть кадр.
   - **Просмотр** — кадр рядом с карточкой, промптом, входами; чек-лист по четырём осям
     (манера, личность, расстановка, детали); вердикт. «Зарегистрировать» → регистрация,
     права, галерея; нарушения на экране. Гейт: все приняты и зарегистрированы.
5. **Стили.** Каталог: манера, палитра, `fits`, эталоны с «почему». Кнопка пересборки
   страницы. Создание и правка направлений — вторая версия.
6. **Задания.** Список, статусы, длительность, лог, «снять из очереди».

## 9. Визуальный контракт

Направление 11, макет `panel/mockup.html`:

  поле; серая `#eef0f3` правая колонка очереди;

  машинный — в Plex Mono;

## 10. Ошибки и восстановление

- Codex падает молча: проверка файла, вторая попытка — правило проекта.
- Плохой результат агента: валидатор, повтор с претензиями, затем `failed` и правка руками.
- Крах сервера: `interrupted`, повтор с готовых файлов.
- Регистрация отказывает, если промпт не пересобирается байт-в-байт; панель показывает
  сообщение как есть.
- Правка карточки после генерации: панель помечает кадр устаревшим (хеш карточки не совпадает
  с тем, что был при генерации — берётся из `plan.json`, куда `scene` записывает `card_sha256`),
  и предлагает перегенерировать.

## 11. Отложено во вторую версию

Область анализа по диапазону абзацев; пороги классификации в настройках; слияние имён и

пары A/B; точечная правка кадра (`edit-target`); новая партия из прежней; теги причин брака и
статистика; коммит и пуш из панели; экспорт логов; автозамер ключа кадра против `palette_en`.

## 12. Проверка

pytest, только стандартная библиотека в коде панели:

- `tests/test_panel_jobs.py` — запись и чтение заданий, перезапуск помечает `interrupted`,
  отмена очереди и прерывание подпроцесса;
- `tests/test_panel_agent.py` — поддельный `codex` (скрипт на `PATH` теста, пишет файлы по
  переменной окружения; для картинок — минимальный валидный PNG 1×1): инструкция содержит
  скилл, книгу и контракт; повтор с претензиями; посторонние изменения ловятся;
- `tests/test_panel_validators.py` — все проверки §6 на фикстуре из трёх абзацев;
- `tests/test_panel_api.py` — `http.client` к серверу на свободном порту с временным
  репозиторием: приём TXT, индекс, отметки, создание партии, вердикт, регистрация.
