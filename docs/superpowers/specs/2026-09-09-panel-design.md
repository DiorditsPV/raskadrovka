# Панель управления «Раскадровки» — дизайн

Дата: 2026-09-09. Основа: разбор функционала и четыре вопроса с ответами «A» (сессия
2026-09-08), макет `panel/mockup.html` (тег `v2-panel-direction-11`), контракты
`docs/superpowers/specs/2026-09-07-raskadrovka-design.md`.

## 1. Цель и рамки

Локальное веб-приложение, из которого книга проходит весь путь до иллюстраций без терминала:
загрузить файл, настроить разбор, отобрать героев и сцены, собрать библию и листы, написать
карточки, сгенерировать кадры, принять их и опубликовать галерею. Отдельная область — стили.

Первая версия — **вертикальный срез**: одна книга через все этапы, каждый экран минимальный,
всё на настоящих данных Red Rising, которые уже лежат в репозитории. Что отложено — в §11.

Панель ничего не хранит у себя. Состояние — файлы репозитория по действующим контрактам;
панель их читает, пишет и запускает те же скрипты, что и человек в терминале. Любой шаг можно
сделать руками, и панель это увидит.

## 2. Принятые решения

| вопрос                                                                   | решение                                                                                  |
|--------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| Кто исполняет шаги с суждением (библия, аудит, карточки, стиль из книги) | Панель сама вызывает агента, без диалога                                                 |
| Кто отбирает героев и сцены                                              | Человек на гейте; без отметок «дальше» не работает                                       |
| Какой агент                                                              | Codex CLI — тот же, что рисует; скиллы читает из `.claude/skills/` по указанию в задании |
| Объём первой версии                                                      | Вертикальный срез                                                                        |

Допущения, принятые без возражений: сервер на стандартной библиотеке Python 3.10 в `panel/`,
одна HTML-страница без сборки; задания живут в процессе сервера, очередь и логи — в
игнорируемом `cache/`; git руками (панель показывает статус); статические `index.html` и
`styles/index.html` остаются публичной витриной, панель их пересобирает.

## 3. Архитектура

```text
panel/
  server.py        ThreadingHTTPServer: GET /api/* — JSON из файлов, POST/PUT /api/* — действия,
                   GET /file/<путь> — картинки и тексты из разрешённых папок, GET / — страница.
                   Здесь же обработчики заданий: они связывают scripts/ и агента с очередью
  jobs.py          очередь: один рабочий поток, задания по одному, запись в cache/panel/jobs/
  agent.py         Codex: сборка инструкции из шаблона, запуск, проверка результата, повтор
  validators.py    контрактные проверки записей библии и карточек — общие для агента и редактора
  settings.py      значения по умолчанию и чтение cache/panel/settings.json
  tasks/
    bible-entry.md шаблон задания «запись героя в библию с аудитом»
    scene-card.md  шаблон задания «карточка сцены»
  index.html       одна страница, экраны переключаются на месте, опрос /api/jobs раз в 2 с
  mockup.html      визуальный контракт (не исполняется)
scripts/
  generate_sheet.py   лист персонажа через Codex — из scratchpad, с CLI
  generate_scene.py   кадр сцены через Codex — из scratchpad, с CLI
```

Сервер импортирует `scripts/` как библиотеку: `ingest_book.ingest()`, `index_book`,
`build_prompt.build()`, `register_result.register()`, `check_rights.check_all()`,
`build_gallery.main()`, `build_styles_page.main()`. Codex — только подпроцессом.

Один рабочий поток нарочно: Codex один, кадры идут по одному, очередь читаема. Быстрые
детерминированные шаги (разбор, индекс, сборка промпта, регистрация) тоже идут через очередь,
чтобы порядок был один и лог общий.

Загрузка книги — multipart, разбирается стандартным `email.parser.BytesParser`; файл ложится в
`books/<slug>/source/`. Раздача `/file/` — только из `output/`, `styles/refs/`,
`compositions/refs/`, `books/*/characters/`, `books/*/*/input/`, `books/*/*/prompt/`, с
проверкой, что путь после `resolve()` лежит внутри корня.

## 4. Задания и очередь

Задание — JSON в `cache/panel/jobs/<id>.json`:

```json
{"id": "20260909-1041-07-sheet-ugly_dan", "kind": "sheet", "args": {"slug": "…", "key": "ugly_dan"},
 "status": "running", "created": "…", "started": "…", "finished": null,
 "attempts": 1, "error": null, "log": "cache/panel/jobs/<id>.log"}
```

Статусы: `queued`, `running`, `done`, `failed`, `interrupted`, `cancelled`. При старте сервера
задания в `running` помечаются `interrupted`, а стоявшие в `queued` возвращаются в очередь:
перезапуск панели — дело обычное и не должен тихо терять работу. Повторный запуск любого вида
пропускает уже существующие результаты — так уже работает раннер сцен.

Задание, у которого вид и аргументы совпадают с уже открытым, в очередь не берётся: ответ
409 с номером того задания. Шаг с суждением идёт минутами, и второй запуск того же — не
удвоенная скорость, а два Codex на одном файле.

Снятие задания на ходу гасит и повтор: убитый процесс со стороны раннера неотличим от
неудачной попытки, и без явного признака «снято» вторая попытка началась бы сама.

Виды заданий первой версии:

| kind          | что делает                                              | чем                                                |
|---------------|---------------------------------------------------------|----------------------------------------------------|
| `ingest`      | файл → `book.json`, `cache/<slug>/paragraphs.jsonl`     | `ingest_book`                                      |
| `index`       | индекс лиц, мест, кандидатов; параметры и диапазон глав | `index_book`                                       |
| `bible-entry` | запись героя с локаторами и аудитом                     | Codex по `tasks/bible-entry.md`                    |
| `sheet`       | лист персонажа                                          | `generate_sheet` (Codex)                           |
| `scene-card`  | карточка сцены партии                                   | Codex по `tasks/scene-card.md`                     |
| `prompt`      | промпт сцены в `prompt/`                                | `build_prompt`                                     |
| `scene`       | кадр сцены                                              | `generate_scene` (Codex)                           |
| `register`    | записи манифеста по плану, регистрация, права, галерея  | `register_result`, `check_rights`, `build_gallery` |
| `styles-page` | пересборка `styles/index.html`                          | `build_styles_page`                                |

`POST /api/jobs/<id>/cancel`: из `queued` — в `cancelled`; из `running` — убить подпроцесс, в
`cancelled`; файл-результат, если успел появиться, остаётся.

## 5. Раннер агента

Одно задание с суждением — одна сущность: один герой, одна сцена. Проверка и повтор точечные.

**Инструкция** собирается из `panel/tasks/<kind>.md` подстановкой полей. Обязательные части:
какой скилл прочесть и следовать ему (`.claude/skills/raskadrovka-characters/SKILL.md` или
`raskadrovka-book`); книга и сущность; где читать текст (`python3 scripts/show_paragraphs.py`,
абзацы из индекса); куда и по какому контракту писать; что не трогать; не коммитить.
Шаблоны коммитятся — они часть провенанса библии и карточек.

**Запуск:** `codex exec -s workspace-write --skip-git-repo-check -C <корень> --ephemeral
"<инструкция>"` с закрытым stdin, таймаут из настроек (по умолчанию 20 минут), лог в файл задания.
Сама командная строка берётся из настроек (`codex_cmd`, §6) списком аргументов, инструкция
подставляется на место `{prompt}`; в коде лежит только значение по умолчанию. Иначе тест не
может подсунуть поддельный `codex`, а человек — сменить профиль или модель, не правя панель.

**Проверка результата** (`validators.py`), после каждой попытки:

- ожидаемый файл существует и разбирается как JSON;
- проходит контрактные проверки своего вида (§6);
- в дереве изменились только ожидаемые пути. Дерево во время работы почти всегда грязное,
  поэтому сравниваются **два снимка** `git status --porcelain` — снятый прямо перед запуском
  Codex и снятый после: провал даёт разница множеств, а не сам факт правок. Ожидаемые пути:
  `bible-entry` — `books/<slug>/bible.json`; `scene-card` — `<партия>/scenes/<NN>-*.json`;
  `scene` — кадр в `output/` и `<партия>/metadata/plan.json`, куда задание пишет `card_sha256`.
  Посторонние изменения — провал с перечнем, панель их не откатывает.

Провал → одна повторная попытка, в инструкцию дописываются претензии валидатора дословно.
Второй провал → задание `failed` с отчётом; сущность правится руками в редакторе панели.

**Заготовки для агента**, чтобы он не выбирал имена сам: у карточки панель задаёт порядковый
номер `NN`, агент выбирает только слаг; валидатор ищет файл по префиксу `scenes/NN-`.

## 6. Данные и контракты

Действующие контракты не ломаются. Расширения:

**`bible.json`, герой** — поле `audit`: десять атрибутов с баллом `0 | 0.5 | 1`, ключи
`age, build, face, eyes, hair, skin, clothing, gear, marks, bearing`; `understanding` равен их
сумме. Проверка: ключи ровно эти, значения из множества, сумма сходится.

**У претензии валидатора два уровня.** `error` — запись противоречит себе или книге: локатор
указывает не на ту главу, балл не сходится с клетками, английское поле написано кириллицей.
`missing` — поля контракта в записи ещё нет; чаще всего оттого, что запись писали до того,
как поле появилось: разбивка `audit` — ровно такой случай, все восемь записей Red Rising
старше её. Красным горит только `error`; иначе «не доделано» и «сломано» неразличимы, экран
краснеет целиком и перестаёт что-либо сообщать. Уровень по умолчанию — `error`, исключение
называется явно: забытая обёртка должна делать претензию строже, а не безобиднее.

**`<партия>/metadata/plan.json`** — что задумано до появления кадров:

```json
{"short": "proba", "style": "tush-i-plashki",
 "scenes": [{"order": 1, "chapter": 2, "paragraphs": [57, 58], "id": null, "card_sha256": null,
             "style": null, "style_refs": ["ref-01", "ref-03"], "composition": "01-dvoe-litsom"}]}
```

`id` заполняется, когда агент написал карточку; `card_sha256` — хеш карточки в момент
генерации кадра, его пишет задание `scene`; `style` у сцены — только для партии-пробы, где
каждая сцена идёт своим направлением, иначе `null` и берётся общий.

`short` — короткое имя партии в имени файла кадра
(`output/<книга>--<short>--<направление>--<карточка>.png`). Отдельное поле, а не имя папки:
папка называется `01-proba-stiley`, а в именах кадров стоит `proba`, и вывести одно из другого
нельзя. Панель предлагает `short` при создании партии и проверяет, что он не занят.

**Кто заводит запись в манифесте.** `register_result.register()` умеет только обновлять уже
существующие записи `scenes`: он читает у записи `card`, `style`, `style_refs`, `composition`,
`prompt`, `output` — то есть замысел, которого сам не знает. Поэтому задание `register` перед
вызовом `register()` **досевает** манифест: для каждой сцены плана, у которой есть карточка и
кадр, но нет записи, оно создаёт запись из плана и карточки —

| поле                        | откуда                                                           |
|-----------------------------|------------------------------------------------------------------|
| `id`                        | `<направление>--<имя карточки без расширения>`                   |
| `title`, `caption`, `order` | карточка (`title` + ` — <направление>`, если стиль у сцены свой) |
| `style`                     | сцена плана, иначе общий `style` плана                           |
| `style_refs`, `composition` | план сцены                                                       |
| `card`, `prompt`            | `scenes/<файл>.json`, `prompt/<id>.txt`                          |
| `output`                    | `../../../output/<книга>--<short>--<id>.png`                     |

Существующие записи не переписываются: хеши, входы и снимки `input/` остаются делом
`register()`. Так замысел заводит панель, а факт по-прежнему пишет один скрипт.

**Листы: принятие без нового поля в библии.** Задание `sheet` из панели пишет лист и промпт в
`cache/panel/<slug>/sheets/<key>.png|.txt`, а не в `characters/`. «Принять» переносит файл в
`books/<slug>/characters/<key>.png` и записывает в библию `sheet`, `sheet_sha256`,
`sheet_prompt` — ровно как сегодня делает человек. Эти три поля ведёт панель, а не агент:
задание `bible-entry` переписывает запись целиком и роняет их, поэтому обработчик запоминает
их до запуска и возвращает после — судить агенту, вести учёт панели. «Отклонить» переносит файл в
`refs-local/sheets-rejected/<key>-<дата>.png`. «Перегенерировать» при принятом листе сначала
переносит прежний в `refs-local/sheets-rejected/` и снимает поля из библии. Так в библии по
определению лежат только принятые листы, и признак «принят» — наличие `sheet` с совпадающим
хешем. `generate_sheet.py` из терминала пишет сразу в `characters/`: человек, запустивший его
сам, и есть приёмка.

**`<партия>/metadata/review.json`** — вердикты, коммитятся:

```json
{"03-ugly-dan-kidaet-kamen": {"verdict": "accepted", "reason": "", "at": "2026-09-09T10:41:07"}}
```

`verdict`: `accepted`, `regenerate`, `rejected`. Регистрация доступна, когда у каждой сцены
плана вердикт `accepted`.

**Карточка сцены** — проверки валидатора (те же, что покажет редактор):

- отрывок — целые абзацы: каждый абзац находится по `paragraph_sha256`, абзацы подряд, одна глава;
- локатор вычисляется из отрывка, а не берётся из файла: панель перезаписывает `locator`;
- для `protected`: ≤ 2 абзацев, ≤ 1500 знаков, сумма по книге ≤ 3 %;
- `invariants` — ключи библии, у каждого есть принятый лист;
- `composition` — `null` или id шаблона из `compositions/templates/`;
- `details` непустой; цветовые эпитеты в `details`/`setting`/`mood` — предупреждение, не провал
  (словарь: названия цветов и «-цветный», «свечение» с цветом);
- `frame.characters[].ref` ⊆ `invariants`.

**Локальное, не в git** — `cache/panel/<slug>/panel.json`:

```json
{"toc_confirmed": true,
 "heroes": {"Darrow": {"key": "darrow", "in_bible": true, "needs_sheet": true}},
 "places": ["Lykos"],
 "scenes": [{"chapter": 2, "paragraphs": [57, 58], "note": "Урод Дэн кидает камень"}],
 "index_params": {"per_chapter": 3, "window": 2, "total": null, "min_mentions": 4, "chapters": [1, 3]}}
```

Ключ героя (`key`) — транслитерация имени из индекса, редактируется человеком до сборки библии.

**Настройки** — `cache/panel/settings.json`, при отсутствии — значения по умолчанию из кода:

```json
{"codex_cmd": ["codex", "exec", "-s", "workspace-write", "--skip-git-repo-check",
               "-C", "{root}", "--ephemeral", "{prompt}"],
 "timeout": 1200, "attempts": 2, "max_style_refs": 3}
```

`{root}` и `{prompt}` подставляются панелью; остальные аргументы идут как есть.

## 7. API

Все ответы — JSON; ошибки — `{"error": "…"}` с кодом 400/404/409. Действия, которые долго
идут, возвращают `{"job": "<id>"}`.

| метод и путь                                                          | что                                                                                                       |
|-----------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------|
| `GET /api/books`                                                      | книги с прогрессом по этапам                                                                              |
| `POST /api/books`                                                     | multipart: файл + метаданные + права + параметры разбора → job `ingest`                                   |
| `GET /api/books/<slug>`                                               | `book.json`, оглавление, `panel.json`, состояние гейтов                                                   |
| `PUT /api/books/<slug>/panel`                                         | отметки: оглавление подтверждено, герои, места, сцены, параметры индекса                                  |
| `POST /api/books/<slug>/index`                                        | job `index` с параметрами из `panel.json`                                                                 |
| `GET /api/books/<slug>/index`                                         | `cache/<slug>/index.json`                                                                                 |
| `GET /api/books/<slug>/paragraphs?chapter=&from=&to=&grep=`           | абзацы из кеша — читалка                                                                                  |
| `GET /api/books/<slug>/bible`                                         | `bible.json`                                                                                              |
| `PUT /api/books/<slug>/bible/<key>`                                   | правка записи руками; валидатор                                                                           |
| `POST /api/books/<slug>/bible/<key>`                                  | job `bible-entry`                                                                                         |
| `PUT /api/books/<slug>/bible/<key>/audit`                             | правка клеток аудита                                                                                      |
| `POST /api/books/<slug>/sheets/<key>`                                 | job `sheet`; `{"regenerate": true}` убирает прежний лист в `refs-local/sheets-rejected/`                  |
| `PUT /api/books/<slug>/sheets/<key>`                                  | `{"accepted": true}` или `{"rejected": true}`                                                             |
| `GET /api/books/<slug>/batches`                                       | партии с состоянием                                                                                       |
| `POST /api/books/<slug>/batches`                                      | создать партию: имя, текст запроса, направление, сцены из отбора → папка, `plan.json`, README с маркерами |

| `POST /api/books/<slug>/batches/<b>/generate`                         | jobs `prompt` + `scene` на сцены без кадра; `{"scenes": [...]}` — на выбранные                            |
| `PUT /api/books/<slug>/batches/<b>/review/<id>`                       | вердикт; `regenerate` удаляет кадр и ставит job                                                           |
| `POST /api/books/<slug>/batches/<b>/register`                         | job `register`                                                                                            |
| `GET /api/styles`                                                     | направления с эталонами                                                                                   |
| `POST /api/styles/page`                                               | job `styles-page`                                                                                         |
| `GET /api/jobs`, `GET /api/jobs/<id>`, `GET /api/jobs/<id>/log?tail=` | очередь и логи                                                                                            |
| `POST /api/jobs/<id>/cancel`                                          | снять или прервать                                                                                        |

| `GET /file/<путь>`                                                    | файл из разрешённых папок                                                                                 |

## 8. Экраны первой версии

Слева навигация: **Книги · Стили · Задания**. Внутри книги этапы по порядку, у каждого виден
гейт. Экран этапа — пронумерованные шаги, у каждого состояние и своя кнопка; внизу гейт с
«Назад» и «Дальше»; сверху «Шаг N из 4» с теми же переходами.

1. **Книги.** Список с прогрессом. Форма приёма: файл, slug, метаданные, права с обоснованием,
   параметры разбора. После разбора — оглавление с предупреждениями (глава короче 300 знаков,
   глава больше 25 % книги), «переразобрать». Гейт: «оглавление верное».
2. **Лица и сцены.** Параметры индекса и диапазон глав. Таблицы: лица (упоминания, вид, главы,
   первый абзац, абзацев с внешностью; отметки «в библию», «нужен лист»; правка ключа),
   места, кандидаты (балл, превью, «окрестности» открывают читалку ±3 абзаца, «взять»).
   Сцена вручную: глава и диапазон. Гейт: есть хотя бы один герой с отметкой «нужен лист» и
   одна сцена.
3. **Персонажи.** Шаг 1 — библия и аудит: вкладки героев, полоса из десяти клеток, считка
   «из книги» и «в промпт», кнопки «Собрать запись», «Править описание», «Добрать из книги»
   (открывает читалку с grep-пресетами внешности). Шаг 2 — листы: карточки с принятием,
   перегенерацией, отклонением; «Сгенерировать листы» ставит задания на героев с аудитом ≥ 8
   без принятого листа. Шаг 3 — в библии без листа, тумблер «нужен лист». Гейт: у всех с
   отметкой лист принят.
4. **Партии.** Список; создание. Внутри партии вкладки:
   - **Карточки** — план сцен, «Написать карточку» на сцену и «Написать все», редактор полей
     `frame` с живыми проверками §6, предпросмотр промпта. Гейт: все карточки зелёные.
   - **Генерация** — эталоны и шаблон на сцену, «Сгенерировать», прогресс по сценам, попытки,
     хвост лога, «Остановить». Гейт: у всех сцен есть кадр.
   - **Просмотр** — кадр рядом с карточкой, промптом, входами; чек-лист по четырём осям
     (манера, личность, расстановка, детали); вердикт. «Зарегистрировать» → регистрация,
     права, галерея; нарушения на экране. Гейт: все приняты и зарегистрированы.
5. **Стили.** Каталог: манера, палитра, `fits`, эталоны с «почему». Кнопка пересборки
   страницы. Создание и правка направлений — вторая версия.
6. **Задания.** Список, статусы, длительность, лог, «снять из очереди».

**Что закрепило ревью дизайна 2026-09-10** (замеры, а не вкус; Lighthouse 100 по доступности):

- контраст текста не ниже 4.5:1. Отсюда точные значения токенов: вторичный текст на сланце

  — 3.51 с белым);
- обводка фокуса на сланцевой боковине белая: акцентная совпадала с фоном и фокус исчезал;
- шкала кеглей ровно шесть ступеней — 12, 13, 14, 16, 18, 24. Ни 11, ни 15, ни 17: лишнее
  целое между ступенями не оттенок смысла, а шум на плотном экране;
- широкое содержимое прокручивается внутри своего контейнера. Таблица персонажей без этого
  вылезала из колонки и роняла кнопки на очередь;
- пороги раскладки: до 1300 px очередь уходит вниз под рабочую колонку (не под боковину —
  та липкая и накрыла бы карточки), до 820 px всё встаёт одной колонкой;
- статус не кодируется одним цветом: у метки есть слово, у клетки аудита — форма
  (полная, половинная, пустая), у полосы аудита — текстовая подпись с просевшими клетками;
- имя элемента для чтения с экрана собирается из его содержимого (скрытый `.sr`-текст), а не
  подменяется `aria-label`: подменённое имя расходится с видимой надписью;
- задание с суждением идёт минутами, поэтому у каждого в очереди видны часы: идущее считает
  вперёд, законченное показывает, сколько заняло и когда кончилось.

**Что закрепила критика UX того же дня** (`/impeccable critique`, две изолированные оценки,
исходный балл 18/40 по Нильсену):

- **Экран живёт в адресе.** `#/книги`, `#/партии/<партия>`. Без этого вкладка «Партии» изнутри
  партии выглядела рабочей и ничего не делала, перезагрузка сбрасывала на «Книги», а сослаться
  на экран было нечем.
- **Этап пройден по гейту, а не по непустоте.** Один лист из восьми — начатый этап, не
  пройденный. Галочка приберегается для гейта, начатый этап несёт номер в зелёном кольце, а
  подпись — долю («листов 4 из 8»). Иначе галочка перестаёт что-либо означать.
- **Кадры одной сцены подписываются тем, чем различаются.** Партия-проба существует, чтобы
  сравнивать; различие «с шаблоном» / «без шаблона» нельзя оставлять тире в служебной строке.
  Совпадающие поля из подписей убираются, мета-строка сцены помечается как замысел («по плану»).
- **Задание называет, про кого оно.** Имя героя, вид задания по-русски, часы со знаменателем
  таймаута, место в очереди, число попыток. `queued` и `running` — разные слова: пятый в
  очереди начнёт через час, и «собирается…» про него — неправда.
- **Штатное событие не красят красным.** `interrupted` — обычное дело по §4, у него
  нейтральная метка и кнопка «Собрать заново», как и у `failed`.
- **Действие называет свою цену.** У героя с годной записью кнопка — «Собрать заново», и лид
  говорит, что прежняя запись будет переписана и это 10–16 минут.
- **Смысл не прячется в подсказку.** Просевшие клетки аудита пишутся текстом, а не только в
  `aria-label`; поля контракта называются по-русски («балл», «аудит»), а не ключами.
- **Лог разворачивается в рабочую колонку.** В колонке очереди это 25 знаков в строке — а это
  единственное окно внутрь задания, которое идёт минутами.
- **Картинки отдаются с меткой версии, а не с запретом кеша.** Кадры и листы весят мегабайты,
  за обход панели их просили по два-три раза; `ETag` оставляет свежесть и убирает повтор.
  У каждой картинки есть размеры — иначе раскладка прыгает по мере загрузки.
- **Опрос отступает.** Две секунды нужны, пока что-то идёт; в покое восемь, на скрытой вкладке
  опроса нет вовсе.

## 10. Ошибки и восстановление

- Codex падает молча: проверка файла, вторая попытка — правило проекта.
- Плохой результат агента: валидатор, повтор с претензиями, затем `failed` и правка руками.
- Крах сервера: `interrupted`, повтор с готовых файлов.
- Регистрация отказывает, если промпт не пересобирается байт-в-байт; панель показывает
  сообщение как есть.
- Правка карточки после генерации: панель помечает кадр устаревшим (хеш карточки не совпадает
  с тем, что был при генерации — берётся из `plan.json`, куда `scene` записывает `card_sha256`),
  и предлагает перегенерировать.

## 14. Что сделано 10 сентября: цепочка целиком

Панель умела один вид заданий из девяти, и это был её главный дефект: три экрана из четырёх
не делали ничего. Теперь путь проходится от файла книги до зарегистрированного кадра, не
выходя в терминал.

| Вид           | Кто делает                          | Где кнопка                              |
|---------------|-------------------------------------|-----------------------------------------|
| `ingest`      | `ingest_book`                       | «Книги» → «Завести книгу»               |
| `index`       | `index_book`                        | «Книги» → карточка книги                |
| `bible-entry` | Codex по `tasks/bible-entry.md`     | «Персонажи» → «Собрать запись»          |
| `sheet`       | `generate_sheet` (Codex)            | «Персонажи» → «Сделать лист»            |
| `scene-card`  | Codex по `tasks/scene-card.md`      | партия → «Написать карточку»            |
| `scene`       | `generate_scene` (Codex)            | партия → «Нарисовать кадр»              |
| `register`    | `register_result` + права + галерея | партия → «Проверить и зарегистрировать» |

`prompt` отдельным заданием не стал: промпт собирает `scene` перед генерацией и кладёт в
`<партия>/prompt/` **до** снимка дерева — иначе он попадает в посторонние правки собственного
задания. `styles-page` остаётся терминальным шагом.

**Загрузка книги.** Файл приходит base64 в JSON и ложится сразу в `books/<slug>/source/` —
единственное место, где тексту книги позволено лежать; папка вне git. Форматы fb2, epub, txt,
предел 40 МБ. Разбор заводит и пустую `bible.json`, чтобы экран «Персонажи» новой книги
работал сразу.

**Приёмка листа.** Генератор кладёт лист в `cache/panel/<книга>/sheets/<ключ>.png` вместе с
`<ключ>.json` (промпт и хеш) и не трогает ни книгу, ни библию. «Принять» переносит файл в
`books/<книга>/characters/` и пишет `sheet`, `sheet_sha256`, `sheet_prompt`; «Отклонить»
стирает. Из терминала `generate_sheet.py` пишет сразу в книгу: там приёмка — сам запуск.
Раздача файлов расширена ровно одним шаблоном `cache/panel/*/sheets/*`; разобранный текст
книги рядом в `cache/<книга>/` наружу не выходит.

**`subject_en` в контракте записи.** Одна английская фраза о том, кто это: возраст, пол,
занятие, место. Из внешности не выводится, в промпт листа идёт первой строкой `Subject:`.
Пишет её агент — **не человек**: книгу читал он. Панель поля для неё не показывает; у героя
без `subject_en` кнопка листа выключена и говорит, что запись надо собрать.

**Кого вести дальше — называет индекс.** Экран «Персонажи» начинается со списка имён, которые
индекс нашёл в книге, с числом упоминаний. «Завести запись» запоминает соответствие
«имя из книги → ключ» в `cache/panel/<книга>/panel.json` и ставит задание. Индексатор научился
отбрасывать слова, которые почти всегда стоят первыми в предложении («Well», «Because»,
«Something»): без этого список наполовину состоял из мусора.

**Одна навигация вместо двух.** Вкладки в шапке дублировали этапы в боковине — четыре кнопки
в двух местах. Вкладки убраны; в шапке живёт то, чего в этапах нет: выбор книги. Этапы в
боковине — единственная навигация.

**Порядок очереди.** Задания приходят от новых к старым — так читается история; очередь
читается наоборот. Идущее задание теперь первое, ждущие идут в том порядке, в каком их
возьмут. «Показать все (N)» и правда показывает все: за остальными панель ходит на сервер,
а не режет свои же двенадцать.

**Устаревшие результаты видны.** Запись героя переписали после листа — на строке появляется
«лист по прежней записи». То же для кадров показывает `register --check`: «промпт на диске не
совпадает со сборкой». Из восьми кадров пробной партии шесть собраны до того, как переписали
запись Дэрроу.

Проверка: 83 теста, из них `tests/test_panel_chain.py` проходит цепочку целиком на поддельном
Codex — файл, разбор, индекс, запись, лист, приёмка, партия, карточка, кадр, регистрация.
Настоящий Codex: лист Ио собран за 1 м 53 с.

**Не сделано и названо вслух:** приёмки кадра (принять/отклонить/перегенерировать) нет —
кадры только складываются рядом; «Стили» по-прежнему витрина, эталон из панели не
сгенерировать; контактного листа для партии на сорок сцен нет; «Убрать законченные» стирает
историю без счёта и подтверждения.

## 15. Раскладка «Персонажей»: что было сломано

Замеры на 2560×1288, книга из восьми героев.

| Дефект                             | Было                            | Стало                               |
|------------------------------------|---------------------------------|-------------------------------------|
| Миниатюры листов разной ширины     | 187 / 209 / 212 px              | 180×120 у всех трёх состояний       |
| Кнопки приёмки столбиком           | `flex-direction: column`        | в строку, с переносом               |
| Таблица уже колонки                | 1180 из 2014 px                 | 1954 из 2014                        |
| Колонки пляшут от длины имени      | 723 / 167 / 164 / 139 / **125** | доли, `table-layout: fixed`         |
| Высота строк                       | 146–192 px                      | 141 у всех                          |
| Пустая рамка «нет листа»           | 210×140                         | 180×120                             |
| Один абзац причины в каждой строке | 4 копии по 111 знаков           | метка «нужна запись» + подсказка    |
| «аудита нет» и «не хватает: аудит» | в двух колонках                 | одна колонка «Понимание и проверка» |
| Три номера шага на два блока       | 1, 2, 3                         | один шаг «Записи и листы»           |

Причина разной ширины миниатюр — не размеры файлов: `.who` это flex, картинка была гибким
элементом, и рядом с длинным именем и двумя метками её сжимало. Лечится `flex:0 0 auto` и
`min-width:0` на текстовой половине.

Порядок блоков теперь зависит от состояния: пока записей нет, первым идёт список находок
(это единственное, что можно сделать); как только записи появились, первой идёт таблица, а
находки уходят вниз. Пустое состояние называет тот шаг, который мешает сейчас («книга ещё не
разобрана»), и даёт кнопку на экран, где это чинят, — раньше советовало строить индекс
независимо от того, разобрана ли книга.

Узкие окна: у таблицы свой минимум 900 px и прокрутка внутри рамки. При 760 px доля первой
колонки уходила под миниатюру целиком, на имя оставалось 34 px, и «старый Барлоу» вставал
по букве в строку.

### Поля ввода — свои, а не системные

`<select>` без `appearance:none` macOS рисует своим шрифтом и своей рамкой: посреди Unbounded
и Plex это читается как вставка из чужой программы. Общее правило на все селекты: свой шрифт,
рамка `--line`, радиус 5, стрелка — inline-SVG в `background`. Высота совпадает с текстовым
полем (37 px).

`<input type="file">` оформить нельзя вовсе: браузер сам рисует кнопку и надпись «Файл не
выбран», и её даже не перевести. Поэтому поле спрятано (не `display:none` — оно должно
оставаться в форме), видимая кнопка — это `<label for>`, имя и размер выбранного файла панель
пишет сама. `required` со спрятанного поля снят: браузер блокирует отправку формы с невидимым
обязательным полем и не говорит об этом.

Проверка, что чужого не осталось: ни один элемент рабочего поля не имеет системного
семейства шрифтов.


## 16. Оператор: кто исполняет шаги с суждением

Шаги, где нужно суждение — прочитать книгу, собрать запись героя, написать карточку сцены, —
исполняет **оператор**: Codex или Claude. Выбор один на панель, живёт в шапке рядом с книгой
и хранится в `cache/panel/settings.json` (`{"operator": "codex"}`).

Разница между операторами не в уме, а в песочнице, и человек должен её видеть, а не помнить:

|        | команда                                                                     | границы                                                           |
|--------|-----------------------------------------------------------------------------|-------------------------------------------------------------------|
| Codex  | `codex exec -s workspace-write --skip-git-repo-check -C {root} --ephemeral` | песочница: пишет только в рабочий каталог                         |
| Claude | `claude -p --permission-mode bypassPermissions`                             | без песочницы: пишет куда угодно, границы держит проверка задания |

Поэтому в шапке рядом с выбором стоит подпись — «в песочнице» или «без песочницы», — а
в логе каждой попытки шапка называет оператора полностью:

```
=== попытка 1 из 2, оператор Claude — без песочницы: пишет куда угодно, границы держит
проверка, 2026-09-10 19:15:29 ===
```

**Рисование выбора не имеет.** Инструмент `image_gen` есть только у Codex, поэтому
`generate_sheet.make` и `generate_scene.make` зовут `agent.run(..., operator=settings.DRAWS)`,
и смена оператора листы и кадры не трогает. В шапке это сказано вслух: «рисует всегда Codex».

Устройство: таблица операторов — в `panel/settings.py`, команда каждого лежит в настройке
`<ключ>_cmd`, а не в таблице, чтобы тест подменял `codex_cmd`, как и раньше, а человек менял
профиль или модель, не правя панель. Неизвестное имя оператора — ошибка, а не тихий откат
к Codex: подменённый молча оператор хуже упавшего задания, потому что в логе он назван
правильно, а работал другой.

Чего сознательно нет: выбора модели (`--model`) и выбора оператора на каждое задание.
Первое — настройка профиля оператора, а не панели; второе превращает одно решение в восемь.

## 17. Понимание героя: добор и объяснённые пробелы

Первый заход по книге даёт то, что лежит на виду, и для второстепенных героев этого мало:
Барлоу 5.0, Кирэн 4.5, мать Дэрроу 6.0 из десяти. Балл честный — книга правда не описывает
их лица. Но лист персонажа при таком балле не сделать, а рисовать их надо.

### Добор (`bible-refine`)

Второй заход **только по просевшим клеткам** (`audit[k] != 1`), с другим правилом чтения.
Три источника, в этом порядке:

1. **Прямое описание** — слова книги об этом человеке. Клетка 1.
2. **Признак группы, к которой книга прямо причисляет героя** — сословие, Цвет, ремесло.
   Клетка **0.5, никогда не 1**, и три условия сразу: книга называет принадлежность
   (локатор), книга описывает внешность группы (локатор), в `appearance_en` черта помечена
   дословной формулой `inferred from shared <группа> traits`. Читая запись, человек должен
   отличать «книга сказала про него» от «книга сказала про таких, как он».
3. **Молчание книги** — балл прежний, и пишется **пробел**.

У просевшей клетки после добора ровно два исхода: поднятый балл или пробел. Клетка,
оставшаяся просевшей и без пробела, задание не проходит (`check_bible_refine`) — иначе добор
превращается в «посмотрел и ничего не сделал», и панель предложит его снова.

### Пробел

```json
"gaps": {"face": {"why": "черт лица книга не даёт нигде",
                  "looked": "все 10 абзацев с именем Barlow (гл. 1, 2, 8, 9, 16, 22, 32)"}},
"gaps_for": "<sha256 от appearance_en + locators + audit>",
"gaps_at": "2026-09-10T19:19:20"
```

`why` и `looked` — судит агент. `gaps_for` и `gaps_at` ставит **панель**, после проверки:
отпечаток обязан считаться от того, что оказалось в файле. Без `looked` «книга не даёт»
неотличимо от «не искал», поэтому поле обязательное.

Пробел — дорогая улика: агент прочёл книгу и ничего не нашёл. Поэтому пересборка записи его
не выбрасывает (панель возвращает `gaps`, как возвращает поля принятого листа), но и не
выдаёт за свежий: если `gaps_for` не сходится с записью, пробел устарел, панель говорит
«пробелы по прежней записи», и клетка снова просит добора.

### Куда уходит пробел

В промпт листа, отдельным разделом — и только когда пробелы есть:

```
Unspecified: the source does not describe this person's face, eyes or hair. Keep these
ordinary and unremarkable — plain and average, nothing memorable; invent no colour, scars,
tattoos, jewellery, insignia or accessories that the description above does not name.
```

Без пробелов промпт остаётся прежним **до байта** — иначе принятые листы перестали бы
пересобираться. Порядок клеток — как в аудите, а не как в словаре, по той же причине.

Пробелы для промпта и для метки «лист по прежней записи» берутся **одним правилом**
(`validators.fresh_gaps`). Читай генератор и экран разное — только что принятый лист сразу
помечался бы устаревшим, и метка перестала бы что-либо значить.

### Порог

`SHEET_GATE = 7` (было 8). Восемь из десяти книга даёт немногим. Семь — с тем условием, что
недосказанное названо вслух и уходит в промпт разделом «оставь обычным».

Арифметика порога: признаки касты дают 0.5, значит запись, где книга описывает лично `k`
клеток, а остальные выведены из группы, набирает `5 + k/2`. Дойти до 7.0 нельзя без четырёх
клеток, описанных книгой лично про этого человека. Каста одна упирается в 5.0 и порога не
берёт — это не опущенная планка, а планка на другом основании.

**Закрытая запись порога не спрашивает.** Если каждая из десяти клеток либо полная, либо
объяснена пробелом, книга отдала всё, что у неё есть, и порог, который продолжает ждать,
становится тупиком: ждать нечего. Барлоу после добора стоит ровно так — 6.0 при семи
пробелах, и выше ему не подняться никогда. Нижняя граница всё-таки нужна: `CLOSED_FLOOR = 5`,
иначе запись из одних пробелов объявила бы себя готовой, а в листе осталась бы одна фраза
о том, кто это.

На экране это сказано вслух — иначе панель противоречит сама себе: наверху «порог 7»,
а у героя с шестью баллами кнопка листа живая. В колонке понимания у такой записи стоит
«книга отдала всё · порога не спрашиваем».


## 18. Чужая работа в дереве: почему задание её не трогает

Задание идёт минуты — запись героя десять-шестнадцать, кадр две-четыре. Всё это время
в том же репозитории работают другие: человек принимает лист, панель пишет пробелы,
рядом правят код. Агент проверяет себя через `git status`, видит там изменения, которых
не делал, и принимает их за свой мусор.

Это не гипотеза. 11 сентября 2026 задание по книге «Between Two Fires» удалило
`books/pierce-brown-red-rising/characters/kieran.png` — лист персонажа **соседней книги**,
принятый человеком за минуту до того. Аккуратно, с резервной копией в `/tmp`, на первой
попытке, без всякой подсказки. В тот же день так же исчезли листы Барлоу и матери Дэрроу,
а `eo.png` вернулся к версии из `HEAD`.

Защиты три, и они независимы.

**0. Посторонняя правка работу не отменяет.** 11 сентября задание нарисовало лист «Смерти»
за 71 секунду — и было объявлено проваленным, потому что в те же две с половиной минуты
человек принял листы Дельфины и Годфруа. Готовая картинка осталась в кеше без карточки
приёмки, то есть пропала. Отличить правку агента от правки человека, который те же десять
минут работает в панели, по `git status` нельзя, и выбрасывать из-за такой догадки сделанную
работу нельзя тем более: теперь это предупреждение в логе и в отчёте, а не провал. Роняет
задание только настоящий вред — удалённый чужой файл, который вернула страховка.

Вдобавок панель отмечает собственные следы: приёмка листа, возврат прежнего, запись
пробелов (`Panel.note` / `touched_since`). Эти пути из разницы снимков вычитаются — их
сделала панель, а не агент, и знает она это точно, а не по догадке.

**1. Претензия о посторонней правке не уходит агенту.** Разницу двух снимков `git status`
даёт не только агент, а отличить его правку от чужой по `git status` нельзя. Раньше
претензия дописывалась в инструкцию повтора дословно, вместе с «Исправь ровно это», —
и «посторонняя правка в файле X» читалась как «убери X». Теперь посторонние правки
показываются человеку и роняют задание, но в промпт не попадают никогда. Если к самой
работе претензий нет, а в дереве появилось лишнее, второй попытки не будет вовсе:
исправлять нечего, а повтор — это ещё один прогон агента с приказом «исправь».

**2. Запрет в каждом задании.** К любому промпту — шаблонному и собранному из данных —
дописывается `HANDS_OFF`: в дереве работают другие, файл, которого ты не создавал, не твой,
ничего не удаляй и не «наводи порядок». Это самая слабая из трёх защит: она держится
на послушании.

**3. Жёсткие ссылки на чужие файлы.** Перед запуском панель раскладывает жёсткие ссылки
на всё под `books/`, кроме путей самого задания, в `cache/panel/guard/guard-*`. Ссылка
не копирует байты — это вторая дорога к тем же данным, 53 файла за 28 мс. Удалить файл
она не мешает, но после удаления данные живы, и панель возвращает файл на место, пишет
об этом в лог и роняет задание. От правки на месте не спасает — inode тот же, — а от
удаления, замены и `git checkout` спасает.

**Текста книги под страховкой нет нарочно.** На него у нас право читать, а не копировать,
и второй дороги к нему панель не заводит даже жёсткой ссылкой в собственном кеше
(`NEVER_LINK = ('/source/',)`).

Забытые каталоги страховки подметаются при следующем запуске: панель убивают на ходу,
`finally` не отрабатывает, а ссылки тихо держат данные удалённых файлов живыми.

### Чем это не лечится

Коммитом. `books/*/characters/*.png` в git попадают, когда человек решит; до этого они
неотслеживаемые, и удаление такого файла не оставляет следа даже в `git status` — строка
не появляется, а исчезает. Отсюда и отдельная проверка на исчезнувшие строки: она смотрит
на диск, потому что после честного коммита файла не убывает, а после удаления убывает.


## 19. Запись героя на экране: «что в записи»

Десять закрашенных квадратов показывают форму записи и молчат о её содержании: какая клетка
понята, а какая нет, по ним не прочесть. И главное — по ним не видно того, ради чего запись
существует: текста, который уйдёт генератору.

Кнопка «что в записи» в строке героя разворачивает три вещи, в этом порядке:

1. **Десять клеток одной строкой** — квадрат, имя, балл. Чего книга не даёт и где искали
   живёт в подсказке, а не на экране: развёрнутым списком это тридцать строк на героя,
   за которыми промпта уже не видно.
2. **Внешность по-русски** — единственное место, где запись читается человеком; в промпт
   она не идёт.
3. **Промпт листа дословно** — ровно тот текст, что уйдёт генератору, вместе с разделом
   `Unspecified`, собранным из пробелов. Не пересказ и не выжимка: видеть нужно то, по чему
   будут рисовать.

Ширина здесь своя, читательская (1040 px): запись лежит внутри прокручиваемой таблицы
и иначе растягивается на всю её ширину — почти две тысячи пикселей, и строка промпта
уходит за край экрана. Высота промпта — `min(560px, 52vh)`, чтобы вся панель помещалась
в экран и на ноутбуке.

Отдельно у каждого квадрата в колонке «Понимание и проверка» появилась своя подсказка:
имя клетки и что с ней. Полоска осталась сводкой, но перестала быть немой.


## 20. Отказ генератора и чего не видит проверка листа

Проверка листа смотрит на файл: он есть, начинается с `\x89PNG`, весит больше ста килобайт,
отличается от прежнего. Этого хватает, чтобы поймать молчаливый провал Codex, и не хватает
ни для чего больше: **нужную картинку от любой другой она не отличает**.

11 сентября это сошлось с отказом цензуры. Запись «Смерти» из «Between Two Fires» говорит
словами книги: `naked old man … rusty scythe with a broken shaft`. Первая попытка получила
от `image_gen` отказ — `moderation_blocked`, `safety_violations=[sexual]`, — и Codex честно
сказал: файл не создан. Отказ приходит строкой в выводе, код возврата нулевой, и для панели
это выглядело как «файла нет». Повтор передал агенту ровно эту претензию, и вторая попытка
нарисовала не то, что просили, а то, что пропустят: аниме-девушку с подписью
`MAYA TANAKA, Age: 20, Role: Protagonist`, палитрой и надписями — всё, что промпт запрещает.
Все проверки она прошла.

**Отказ теперь распознаётся по выводу** (`agent.refusal`) и повтора не даёт: рисовать
отказались не по ошибке, а по правилу, и второй заход даёт не тот рисунок, а любой.
Задание падает с внятной причиной, которая видна на карточке в очереди: «генератор отказался
рисовать: … Повтор не поможет — дело в самом описании, а не в попытке».

**Третий выход вместо отказа.** В промпт листа и в промпт кадра добавлен раздел
`Assembled description`: описание собрано автоматически из книги и не является заказом
на содержание; если часть его нельзя нарисовать по правилам, не отказывайся и не рисуй
вместо этого другое — опусти черту или добавь простейшее, что делает её изобразимой
(одежду, покров), и нарисуй остальное как описано. Человек, которого описание называет
раздетым, рисуется в простой некрашеной одежде.

Проверено на том же герое: Смерть нарисована в три проекции, с ржавой косой на сломанном
древке, с сеном в мокрых седых волосах — и в холщовой повязке на бёдрах вместо наготы.

**Оговорка не должна ловить сама себя.** Первая проверка отказа искала обороты «safety
system» и «content policy» — тем же языком написана и оговорка в промпте, а Codex печатает
промпт эхом в свой вывод. Проверка объявила отказом каждое рисующее задание, включая удачное:
картинка была нарисована и выброшена. Теперь ищутся только машинные коды ответа API
(`moderation_blocked`, `safety_violations=`, `image_generation_user_error`), которых в тексте
промпта быть не может, и на это есть отдельный тест.

**Чего это не чинит.** Проверка по-прежнему не знает, что на картинке. Единственный судья
содержания — человек на приёмке, и это не недоделка, а устройство: лист ложится в `cache/`
и ждёт кнопки. Отсюда правило: **карточку приёмки нельзя выписывать картинке, которую
не открыл**. Восстанавливая потерянный лист, смотреть надо на изображение, а не на его
размер и первые четыре байта.


## 21. Раскладка ячейки: один шаг вместо склейки строками

Содержимое ячеек таблицы собиралось конкатенацией строк и текло инлайном. Замер показал,
что из этого выходило: соседние плашки стояли в 0 px, плашка и раскрывашка налезали друг
на друга на −1 px, кнопки стояли в 6, плашки у другого героя — в 4. Единой раскладки не было
вовсе; расстояния получались из того, какие пробелы уцелели в шаблонных строках.

**Шаг теперь один и общий:**

|               |                                                    |
|---------------|----------------------------------------------------|
| `.stack`      | 9 px между группами по вертикали, ячейка — колонка |
| `.pile`       | 8 px между кнопками                                |
| `.pile.tight` | 6 px между плашками внутри группы                  |

Кнопка лежит в группе даже когда она одна: иначе одиночная кнопка стоит по другим правилам,
чем пара, и строки перестают выравниваться между собой.

**И повтор, который эта склейка прятала.** В каждой строке таблицы был заново набран абзац
объяснения: «книга отдала всё — порога не спрашиваем: недосказанное уйдёт в промпт как
„оставь обычным“», «пробелы записаны по прежней записи — добор нужен заново». Правило одно
на всю таблицу, а стояло оно у каждого героя. Теперь это плашки с подсказкой — «книга отдала
всё», «пробелы устарели», — а словами в строке остаётся только то, что про эту запись:
какие клетки просели и каких сведений книга не даёт.

Ячейка понимания собирается одной функцией `understandingCell`, а не тремя, которые
склеивали свои куски в общий поток и не знали друг о друге.

**Проверка — замером, а не взглядом.** После правки в таблице из восьми героев не осталось
ни одной пары ближе 5 px, встречаются ровно два зазора — 6 и 8, — строки снова одной высоты
(141 px), и при зажатой до 820 px таблице, когда кнопки встают друг над другом,
вертикальные зазоры те же 6/8/9.


## 22. Выбор — в боковину, метаданные — из книги

**Книга и оператор переехали из шапки в сланцевую боковину**, под этапы, за разделитель.
Это выбор, а не действие, и стоять он должен рядом с остальным выбором. Книги — списком
кнопок, а не выпадающим списком: их немного, и какая открыта, видно не нажимая. Оператор —
две кнопки, Codex и Claude, с подписью «в песочнице · рисует всегда Codex». Системных
`select` в панели не осталось ни одного.

Смена книги экран не меняет: человек смотрел партии — пусть смотрит партии другой книги,
а не возвращается к началу. В шапке остались имя и состояние.

**«Завести книгу» читает файл сам.** `ingest_book.describe` достаёт из fb2 `title-info`
(название, автор, переводчик, язык, дата) и `publish-info` (издательство и год как
«издание»), из epub — `dc:title`, `dc:creator`, `dc:contributor[role=trl]`, `dc:language`,
`dc:date`, `dc:publisher`. У txt метаданных нет — название берётся из имени файла.
`slug_for` складывает слаг из названия транслитом; занятый слаг различает фамилия автора,
дальше — номер.

За человеком остаются **права**: срок охраны из метаданных не выводится, и выводить его
догадкой нельзя.

Файл при этом уходит на сервер один раз: `POST /api/books/meta` кладёт его в
`cache/panel/staged/<хеш>.<ext>`, возвращает метаданные и токен, а `POST /api/books`
по токену забирает уже лежащий файл и убирает черновик. Это единственное место вне
`books/<slug>/source/`, где тексту книги позволено лежать, и живёт он там минуты;
забытые черновики подметаются через шесть часов.

Над полями формы стоит строка о том, что заполнено не человеком: «Из файла: название,
автор, издание, год, слаг. Проверьте и укажите права».


## 23. Сетка под страницу панели

`panel/index.html` — один файл без сборки: ни компилятора, ни линтера, и опечатку в нём
ловить нечему. Дважды правка по номерам строк молча уносила лишнее. В первый раз незакрытым
остался `<div class="audit-block">` — браузер заглотил внутрь него половину ячейки, и вся
раскладка перестала работать. Во второй раз вместе с двумя удалёнными функциями уехала
третья, `disclose`, и экран «Персонажи» перестал открываться вовсе: ни один тест этого
не заметил, потому что ни один тест страницу не открывает.

`tests/test_panel_page.py` читает файл как текст и проверяет четыре вещи:

- теги, открытые в шаблонах, закрыты (`div`, `span`, `button`, `table`, `tr`, `td`);
- каждое вызываемое имя объявлено — это и ловит уехавшую функцию;
- у каждого действия из `ACTIONS` есть разбор в обработчике нажатия;
- и наоборот: разбираемое действие перечислено в `ACTIONS`, иначе селектор его не поймает.

Проверки грубые нарочно. Они не заменяют взгляда на экран и не проверяют смысла — они
ловят ровно тот класс, где правка ломает страницу молча.


## 24. Несколько полос: замки вместо одной очереди

Очередь была одним потоком, задания строго по одному. Почти всё это время панель ждала сеть:
запись героя 423 с, добор 237 с, лист 98 с — книга на пятнадцать героев складывалась
в три часа подряд.

Мешал не поток, а **общий файл**. Две записи героев одной книги правят один `bible.json`
и затрут друг друга; кадры одной партии — один манифест. Всё остальное не спорит.

Поэтому задание объявляет **замки**: исключительный на то, что правит само, общий на то,
чем пользуется, но не меняет. Очередь берёт следующее, только если его замки ни с кем
не пересеклись; задание с занятым замком не снимается с очереди, а пропускается — иначе
одна книга держала бы панель, пока её герои собираются по одному.

| задание                       | общее             | исключительное           |
|-------------------------------|-------------------|--------------------------|
| `ingest`, `index`             | —                 | `книга:<слаг>`           |
| `bible-entry`, `bible-refine` | `книга:<слаг>`    | `библия:<слаг>`          |
| `sheet`                       | `книга:<слаг>`    | `лист:<слаг>/<герой>`    |
| `scene-card`                  | `книга`, `партия` | `карточка:…`             |
| `scene`                       | `книга`, `партия` | `кадр:…`                 |
| `register`                    | `книга:<слаг>`    | `партия:<слаг>/<партия>` |

Таблица живёт в панели, а не в очереди: что с чем спорит — знание о работе, а не об очереди.
Без таблицы всё исключительно на одном ключе, то есть по одному, как было.

**Ширина — видимая настройка** (`jobs`, 1–4), кнопками в боковине под оператором. Цена прямая
и названа вслух: столько же одновременных прогонов Codex и столько же расхода в моменте.
Меняется на ходу — новые полосы поднимаются сразу, лишние уходят, когда доработают своё.

**Очередь говорит, чего ждёт.** «Задания идут по одному» было правдой при одной полосе;
при трёх это враньё — рядом не идёт не потому, что нельзя, а потому что занят файл. Карточка
в очереди называет замок и того, кто его держит: «занято: библия книги — grace». Если дело
не в замке, а в ширине, так и написано: «свободных полос нет, рядом идёт 2».

**Чего это не даёт.** Записи героев одной книги по-прежнему идут по одной: чтобы развести
и их, агент должен перестать писать в общий `bible.json` и писать черновик, который панель
вливает под замком. Это меняет контракт агента, и решение отложено.


## 25. Два языка интерфейса

Репозиторий публичный, и панель должна читаться не только по-русски. Переводится **только
то, что написала сама панель**: подписи, объяснения шагов, кнопки, подсказки. Данные не
переводятся никогда — имена героев, описания внешности, тексты агента и претензии валидатора
остаются как есть, потому что это книга и работа агента, а не интерфейс.

**Ключ перевода — сама русская фраза.** `t('Собрать запись')` ищет её в словаре `EN`; нет
перевода — показывается русская. Так фраза видна в коде на месте, непереведённое деградирует
в читаемое, а не в пустоту или слуг, и словарь нельзя рассинхронизировать с кодом незаметно:
ключ и есть текст.

Подстановки идут отдельно: `t('листов {a} из {b}', {a, b})`. Собирать перевод из кусков
нельзя — порядок слов в языках разный.

Переключатель — в боковине, рядом с оператором и шириной; выбор хранится в настройках
(`lang`), то есть переживает перезагрузку и одинаков во всех вкладках.

Словарь — 341 запись, 267 мест вызова. Что осталось по-русски на английском экране: имя
проекта и данные книги — и это правильно.

**Отдельная ловушка: кеш перерисовки.** Очередь заданий не перерисовывается, пока не
изменился её состав, — иначе открытый лог мигал бы каждые две секунды. После переключения
языка состав тот же, и колонка оставалась русской. Язык добавлен в подпись состава.
